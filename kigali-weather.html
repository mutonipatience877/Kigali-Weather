B Warm-up: waiting without freezing

A server takes time to answer: half a second, sometimes five. An app must not freeze while it waits. Dart has a way to wait without freezing: a Future.

🧠 Toolbox: Future, async and await

A Future is a promise of a value later, like the ticket you get when you order a brochette: you do not have the food yet, but you will.

A function marked async can wait inside it. await means "wait here until the value is ready", and meanwhile the rest of the app keeps working.

Create warmup.dart next to pubspec.yaml, type this, and run it in the Terminal with dart run warmup.dart.

Future<String> orderBrochette() async {
  await Future.delayed(const Duration(seconds: 3));
  return 'Your brochette is ready';
}

void main() async {
  print('1. You order a brochette');
  final order = orderBrochette();
  print('2. While it cooks, you chat with your friends');
  final food = await order;
  print('3. $food');
  print('4. You eat');
}
1. You order a brochette
2. While it cooks, you chat with your friends
(3 seconds pass)
3. Your brochette is ready
4. You eat
🔍 What just happened

Line 2 printed straight away: ordering did not block you. The program only stopped at await order, exactly where it needed the food. That is how your app will wait for the weather while the screen keeps spinning smoothly.

Future<String> reads "a String, later". Future.delayed just pretends to be slow; tonight the slow thing will be a real server.

Break it on purpose: remove the word await from final food = await order; and run again.

3. Instance of 'Future<String>'

You printed the ticket, not the food. Forgetting await is the most common async mistake: when you see Instance of 'Future, an await is missing. Put it back.

1 Look at the data

Before you write any code, look at what the server sends. Open this address in Chrome on your laptop:

https://api.open-meteo.com/v1/forecast?latitude=-1.9441&longitude=30.0619&current=temperature_2m,relative_humidity_2m,wind_speed_10m,weather_code&timezone=Africa%2FKigali
Text like this (your numbers will be different):
{"latitude":-1.93, … "current":{"time":"2026-10-26T12:15","temperature_2m":24.9,"relative_humidity_2m":52,"wind_speed_10m":11.7,"weather_code":3}}
🔍 What just happened

You just used an API: an address that answers with data instead of a web page. Open-Meteo is free and needs no account. The address itself is the question: latitude and longitude say where, and current=... says what you want to know.

The answer is JSON, the language servers and apps use to send data. { } is an object with keys and values, exactly like a Dart Map. Objects can sit inside objects: the weather is inside "current". [ ], when you meet it, is a list.

weather_code is a number that describes the sky: 0 is clear, 3 is cloudy, 61 is rain. You will turn it into words in step 5.

🧠 How a request travels

1. Your app (the client) sends a request over the internet to the server's address. Asking for data is called a GET request: that is what Chrome just did, and what http.get will do.

2. The address carries the question. Everything after ? is a list of parameters, written name=value and separated by &: latitude=-1.9441&longitude=30.0619&current=temperature_2m,.... Special characters are written in code: %2F is a /, so Africa%2FKigali is Africa/Kigali.

3. The server works out the answer and sends back a response: a status code, which says how it went, and a body, the data itself (here, JSON).

Status codeMeaning
200OK: here is your answer
400Your question is wrong (for example a misspelt parameter)
404That address does not exist
500The server itself has a problem

4. All of this takes time, and any step can fail: no internet, a slow network, a server that is down. That is why tonight is about waiting well and failing well.

2 The model and the request

Create a new file, lib/weather.dart. It holds your model and the function that asks the server: no widgets at all.

import 'dart:convert';

import 'package:http/http.dart' as http;

class Weather {
  Weather({
    required this.temperature,
    required this.humidity,
    required this.wind,
    required this.code,
  });

  final double temperature;
  final int humidity;
  final double wind;
  final int code;

  factory Weather.fromJson(Map<String, dynamic> json) {
    return Weather(
      temperature: (json['temperature_2m'] as num).toDouble(),
      humidity: (json['relative_humidity_2m'] as num).toInt(),
      wind: (json['wind_speed_10m'] as num).toDouble(),
      code: (json['weather_code'] as num).toInt(),
    );
  }
}

Future<Weather> fetchWeather() async {
  final url = Uri.parse(
    'https://api.open-meteo.com/v1/forecast'
    '?latitude=-1.9441&longitude=30.0619'
    '&current=temperature_2m,relative_humidity_2m,wind_speed_10m,weather_code'
    '&timezone=Africa%2FKigali',
  );
  final response = await http.get(url);
  if (response.statusCode != 200) {
    throw Exception('The weather server answered ${response.statusCode}');
  }
  final data = jsonDecode(response.body) as Map<String, dynamic>;
  return Weather.fromJson(data['current'] as Map<String, dynamic>);
}

🔍 What just happened

The model. Weather.fromJson turns one JSON object into a Weather. A factory is a constructor that builds the object from something else, here a Map. Every app that talks to a server has fromJson for its models.

Why as num and .toDouble()? JSON does not know the difference between 25 and 25.0. Reading it as num (any number) and then converting is safe whatever the server sends.

The request. Uri.parse turns the address into something http understands. await http.get(url) waits for the answer. statusCode 200 means "OK": anything else is a problem, so you throw an error. jsonDecode turns the JSON text into a Dart Map, and you hand the "current" part to fromJson.

4 No internet

Experiment first. On the emulator, swipe down from the top of the screen twice and turn on Airplane mode. Then hot restart.

The spinner turns forever, and the Run panel shows Unhandled Exception: ClientException with SocketException: Failed host lookup: 'api.open-meteo.com'.

Your app asked a question with no internet, the request failed, and nobody caught the failure. In Rwanda, phones lose the connection all the time: a real app must be ready for it.

Replace the whole _WeatherScreenState class with this:

class _WeatherScreenState extends State<WeatherScreen> {
  Weather? weather;
  bool loading = true;
  String? error;

  @override
  void initState() {
    super.initState();
    load();
  }

  Future<void> load() async {
    try {
      final result = await fetchWeather();
      setState(() {
        weather = result;
        loading = false;
        error = null;
      });
    } catch (e) {
      setState(() {
        loading = false;
        error = 'Could not load the weather. Check your internet connection.';
      });
    }
  }

  void retry() {
    setState(() {
      loading = true;
      error = null;
    });
    load();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Kigali Weather')),
      body: Center(
        child: loading
            ? const CircularProgressIndicator()
            : error != null
            ? Column(
                mainAxisSize: MainAxisSize.min,
                children: [
                  const Icon(Icons.wifi_off, size: 48),
                  const SizedBox(height: 12),
                  Text(error!, textAlign: TextAlign.center),
                  const SizedBox(height: 12),
                  FilledButton(onPressed: retry, child: const Text('Retry')),
                ],
              )
            : Text(
                '${weather!.temperature}°C',
                style: const TextStyle(
                  fontSize: 64,
                  fontWeight: FontWeight.bold,
                ),
              ),
      ),
    );
  }
}
Still in Airplane mode, hot restart: a clear message and a Retry button. Turn Airplane mode off, tap Retry: the weather appears.
🔎 Line by line
CodeWhat it does
bool loading = true; String? error;Two new pieces of State. loading starts true, because the screen opens while loading. error holds the message to show, or null when there is none.
try { ... }Run this code, but be ready: if anything inside fails, jump to catch instead of crashing.
final result = await fetchWeather();If there is no internet, or the server answered badly and fetchWeather did its throw, the code jumps straight to catch: the lines after it in the try are skipped.
setState(() { weather = result; loading = false; error = null; });Success: store the weather, stop loading, no error.
catch (e) { ... }Runs only when something failed. e is the error itself: you could print it to see the details in the Run panel.
setState(() { loading = false; error = 'Could not load...'; });Failure: stop loading, and set a message a person can understand. The user never sees the technical error, only this.
void retry() { setState(...loading = true...); load(); }The Retry button: show the spinner again, clear the error, and try once more.
loading ? ... : error != null ? ... : ...The three states, checked in order: loading first, then error, and only then the data. That order is what makes weather! safe.
🔍 What just happened

try runs code that might fail; catch runs only if it did, instead of crashing. Anything that talks to the internet can fail, so it always goes inside a try.

Every screen that loads data has three states: loading (the spinner), error (the message and Retry) and data (the weather). Your State keeps one variable for each, and build shows the right one. Remember these three: your capstone needs them on every screen that loads data.

🆘 Classic trap

Null check operator used on a null value: you used weather! while weather was still null, for example by showing the data before checking loading and error. Check the states in the right order.

String describe(int code) {
  if (code == 0) return 'Clear sky';
  if (code <= 2) return 'Partly cloudy';
  if (code == 3) return 'Cloudy';
  if (code == 45 || code == 48) return 'Fog';
  if (code >= 51 && code <= 57) return 'Drizzle';
  if (code >= 61 && code <= 67) return 'Rain';
  if (code >= 80 && code <= 82) return 'Rain showers';
  if (code >= 95) return 'Thunderstorm';
  return 'Unknown';
}
IconData iconFor(int code) {
  if (code == 0) return Icons.wb_sunny;
  if (code <= 3) return Icons.cloud;
  if (code == 45 || code == 48) return Icons.foggy;
  if (code >= 95) return Icons.thunderstorm;
  if (code >= 51) return Icons.water_drop;
  return Icons.help_outline;
}

🧠 The pattern for saving a list

Give your model a toJson and a fromJson:

Map<String, dynamic> toJson() {
  return {'name': name, 'bought': bought};
}

factory Item.fromJson(Map<String, dynamic> json) {
  return Item(json['name'] as String, json['bought'] as bool);
}

Then one function saves the whole list, and one loads it back:

Future<void> saveItems() async {
  final prefs = await SharedPreferences.getInstance();
  final list = items.map((item) => item.toJson()).toList();
  await prefs.setString('items', jsonEncode(list));
}

Future<void> loadItems() async {
  final prefs = await SharedPreferences.getInstance();
  final saved = prefs.getString('items');
  if (saved != null) {
    final list = jsonDecode(saved) as List;
    items = list.map((x) => Item.fromJson(x as Map<String, dynamic>)).toList();
  }
}

Call loadItems once when the app opens (from initState, then setState), and saveItems after every change: add, delete, edit, undo.
